## Critical — unresolved: SDK success is not full synchronization success

`BreezSparkWalletProvider.syncNow()` currently sets `lastSyncedAt`, clears the outage record and lets `getBalance()` return `fresh: true` whenever `sdk.syncWallet({})` resolves. That reaches balance visibility, automatic payouts, lifecycle recovery and emergency-exit reachability.

The pinned upstream implementation catches Spark wallet and wallet-state sync errors, turns them into boolean flags, emits an event, and returns `Ok(())`. The public sync response contains no flags. Thus a successful JavaScript promise does not establish that the current wallet balance was synchronized. The subsequent exit-chain collection can fail independently, but is not a documented replacement for checking those wallet-sync flags. This is a source-confirmed contract defect; an actual operator outage was not induced in a funded wallet. [Upstream sync implementation](https://github.com/breez/spark-sdk/blob/0.25.0/crates/breez-sdk/core/src/sdk/sync.rs#L152), [public sync wrapper](https://github.com/breez/spark-sdk/blob/0.25.0/crates/breez-sdk/core/src/sdk/sync.rs#L710).

Waiting for a public `synced` event does not repair this: after the first event, partial syncs can also produce that event. `getInfo({ensureSynced:true})` waits for initial readiness and then reads the local account cache; it cannot prove a later network refresh. [Upstream event emitter](https://github.com/breez/spark-sdk/blob/0.25.0/crates/breez-sdk/core/src/events.rs#L386), [upstream cached info read](https://github.com/breez/spark-sdk/blob/0.25.0/crates/breez-sdk/core/src/sdk/runtime/client.rs#L95).

The local correction stops partial SDK events from clearing a known balance error or declaring a wallet healthy. It **does not claim to fix the remaining `syncWallet()` success assumption**. It is marked in the provider code. No speculative HTTP probe, balance comparison, or log-message parser was substituted for wallet synchronization.

Required resolution: a supported SDK result/event that proves both the wallet and account-state synchronization succeeded, or a narrow upstream SDK fix that propagates those failures into the public call. Test it with the device online but Spark operators unreachable, partial sync failure, and an empty local cache with an existing saved balance. Until then, “fresh”, auto-withdraw’s fresh-read guarantee, outage recovery, and receipt checkpoint advancement remain unproven. Cached history can appear complete even while the SDK has missed a payment.

## Critical — corrected locally

1. **Connections could resurrect removed wallets.** Concurrent callers created separate provider wrappers. Initialization could finish after removal/rebuild and publish a provider, balance or info into an invalid lifetime; an old error could overwrite a newer connection state. Connection attempts now serialize at the store boundary and check wallet lifetime after awaits. Disconnect/reset invalidate work. Tests cover concurrent initialization and removal during initialization. This was an existing race exposed more often by app-wide coordination.
2. **Unknown or failed balance reads could look like empty/fresh wallets.** A failed sync followed by an SDK cache value of zero overwrote saved funds. A later cache read cleared the failure. Home still rendered its legacy numeric fallback rather than the shared known/stale state. Failed cache results now preserve the accepted value or leave it unknown; cache-only reads cannot clear a failure or inherit freshness for a changed value. Home displays an unknown marker or a stale label. Its number display is keyed by wallet so switching accounts does not animate through another wallet's balance. This closes gaps in the PR, subject to the unresolved SDK success contract above.
3. **Auto-withdraw could send after being disabled during synchronization.** The new awaited fresh read widened the interval between reading configuration and sending. The action now rechecks configuration, wallet lifetime and provider identity after that await. A test disables the feature while the read is pending and verifies that no send occurs.
4. **An old invoice lookup could confirm a replacement invoice.** The event path matched the invoice hash, but the resume lookup had no matching guard after its await. A pending connection could also install listeners after Receive closed. Monitor generations and invoice identity now guard completion; polling resolves the current provider after a rebuild. Tests cover late subscription and stale invoice completion. The resume lookup defect predated this PR.
5. **Manual deposit claims were not bound to the quote’s wallet.** The sheet used the currently selected provider at submission and could continue against another wallet after a switch. Claims and offers now carry their owning wallet/outpoint, reject obsolete work, and guard UI publication. An absent explorer UTXO is no longer treated by itself as proof that a failed claim succeeded. The ownership flaw predated the PR; independent live wallets make this boundary particularly important.
6. **Removing Personal could remove an unrelated wallet and leave Personal behind.** Group-member removal changed array indices before the main wallet was spliced using its old index. Removal now resolves the final index again and selects a surviving wallet even when the selected account was a sibling. The regression test includes a third, unrelated wallet. This is a pre-existing defect in the affected deletion flow.

## Important — corrected locally

1. **Old lifecycle work could alter a new owner.** Late failures and exit-kit completion could change health or schedule retries after replacement/stop. Owner identity and epoch checks now cover those continuations. Explicit disconnects remain suspended from automatic wake reconciliation.
2. **One slow account could block both accounts.** Global serialized reconciliation and unbounded ancillary reads could prevent the other account from recovering. Accounts now reconcile independently; coordinator waits have deadlines. A timed-out underlying SDK sync retains its shared waiter until completion, preventing repeated polls from queuing additional syncs behind it. Tests cover hung history, retry recovery, stop, disconnect, and independent progress.
3. **Catch-up silently stopped at 100 receipts.** It now paginates Bitcoin receives before advancing the checkpoint. Outstanding payment IDs survive restart and are rechecked even when their creation timestamp is older than the overlap window.
4. **The 300-ID FIFO could repeatedly announce busy-wallet history.** Deduplication now retains all IDs in the query overlap window and prunes by the completed checkpoint. Pending payments remain separately tracked. Tests replay 350 receipts and test retention/pruning and delayed settlement after restart.
5. **Receipt classification and delivery were misleading.** Token units could be announced as sats. An external payment could be swallowed by a same-amount own-transfer expectation. A delayed SDK event arriving before catch-up after resume could consume the receipt without a toast. Bitcoin filtering, identity-only suppression and origin-independent resume delivery correct those cases. Native `appStateChange` also now participates in foreground detection.
6. **Deposit discovery and claim completion could restore stale UI.** A slower older read could replace a newer list; a submitted claim completing after removal recreated entries. Discovery ordering now rejects obsolete results. Successful submitted claims still record the durable outpoint, but do not revive removed-wallet UI. Explorer failure now throws rather than returning a fabricated empty list.
7. **Non-Spark connections bypassed the new balance contract.** Arkade, LNbits and NWC initialization paths wrote raw balances without freshness/cache metadata. They now publish through the shared acceptance action. Their payment APIs and background behavior were not redesigned.
8. **“Redacted” diagnostics retained arbitrary SDK error messages.** Those can contain payment inputs or addresses. The support diagnostic history now records stages, timings and failure flags without arbitrary error text.

## Minor / explicit limits

- Native Spark-address own transfers have no receiving invoice hash in this flow. They are no longer suppressed by amount alone; a delayed own-transfer receipt can therefore produce a notice. Exact native-transfer identity correlation is a follow-up, not grounds for suppressing unrelated payments.
- Receipt persistence still uses best-effort browser storage. When storage is unavailable, deduplication works in memory; cross-restart at-most-once delivery cannot be guaranteed. The tests cover this degradation, not durable delivery under storage failure.
- Existing build warnings concern large chunks, mixed static/dynamic imports and the browser externalization of `crypto` in the unrelated WireGuard module. No unrelated bundling refactor was made.

External network calls are blocked or replaced with fixtures. No real wallet secret or payment is used. Screenshots are in `output/pr296-review/`.
- Boot tests execute the real boot module with native bridges replaced by controllable fixtures and exercise repeated background/foreground cycles. Component tests execute the real SFC methods. These complement the service tests; they do not emulate OS suspension or the real WASM network.
- No Android device was connected (`adb devices -l` returned an empty list). A native 30-minute background/foreground soak, incoming payments during background/suspension, airplane-mode and operator-only outages, process restart, both accounts receiving concurrently, and native QR camera/decoder recovery are **not verified on hardware**.
- #276 remains separate: local JavaScript coordination cannot deliver a new notification while the OS has suspended the runtime. Reliable suspended-app delivery needs the deferred push/native work.

The two original symptoms share application lifecycle/state ownership problems, but are not a single bug. Multiple-account ownership, stale/unknown presentation, catch-up correctness, SDK synchronization observability and OS-suspended delivery are distinct boundaries. The app-level corrections improve the first three; SDK observability and real-device validation remain release gates.
